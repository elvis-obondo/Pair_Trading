# S2 TARGET: label specification (STEP A; written before any label is built, any model is fitted or the vault is scored)

Task (planner, from the user, 2026-11-20): retrain the S1 model on a MONEY target instead of reach-mu. Fixed by the user: target = net bp per trade; cost = taker; exit = mu or 10 h. The user rules the data fresh for the new target (test months and vault). Discipline anyway: every design choice below is justified from test-month or search evidence and written here before the vault is scored; the vault is scored ONCE, at the end.
This file is STEP A only: the label spec and the sizing. No label build, no fit, no AWS. Step B (ceiling check on the test months) and step C (refit) follow only on the planner's go.
Revision 2026-11-20 (after the planner's missing-mid ruling): sections 2, 3, 5, 6, 7, 8 changed; the old no-forward-fill rule is replaced by section 3.
Revision 2 2026-11-20 (checker review of step A, 3 blocking and 3 minor findings, and the planner's go with the user's words "lets just update the dataset label"): section 3 states the ORDER of the build and that the stops use path minutes 1..k_x; sections 6 and 7 gain src_out_a / src_out_b and the entry-versus-exit source print; section 7's stop is on the PER-LEG flag; section 5 notes the post-t0 median; section 8 records that the vault labels are built (as the user asked) but written to their own file and read by no step before the planner calls the vault scoring. Build code: diagnostics/s2_target_lib.py, s2_target_build.py, s2_g8_slim.py; proofs: s2_target_tests.py.

## 1. Events
- All saved events with their saved trigger, beta, alpha, mu, sigma and z (events.parquet). The signal is unchanged (still built from closes); only the outcome is re-measured. Direction s = +1 if z >= 0 else -1. dir_a = -1 if z >= 0 else +1; dir_b = (+1 if z >= 0 else -1) x sign(beta) (as the engine; a beta < 0 pair has both legs in the same direction).
- SEARCH side: the events S1 used (harness.load_search_events: usable, label_gap = 0). VAULT side: every event of load_vault_event_dates (events.parquet geometry only; labels.parquet is never opened for the vault). S1's own scored vault set (label_gap = 0) is a subset; any comparison with S1 restricts to S1's list.
- Test months = folds 1-7 of the search side, as in COSTS1 (fold 0 is search but not a COSTS1 test month).

## 2. Prices and time alignment (as COSTS1 section 10.1)
- Real mid(coin, stamp) = the ctxs mid_px stamped `stamp` if > 0, else the G8 table mid of the wall-clock minute `stamp` if > 0 (the first snapshot of the minute, 0.3 to 2.7 s after the boundary), else MISSING. The source (ctxs / G8) is stored for the entry mids. The G8 table is a labelled fallback. The two mid sources agree within 1 bp on only 55.0% (vault) and 78.3% (test) of the (coin, minute) pairs both have, with a median gap of 0.77 bp (vault) and 0.06 bp (test) and a 99th percentile near 30 bp, so the source matters and is recorded. (Citation: `diagnostics/costs_nobounce.log`, the G8 CROSS-CHECK blocks, ALL rows, 'within 1 bp'; this is ctxs mid against G8 mid, not close against mid.)
- ENTRY TIMING, stated plainly: entry fills at the mid stamped t0, which is the book 0.3 to 2.7 s after the bar close. y therefore assumes ZERO decision and order latency. Any real delay is NOT in y. The entry-delay question (COSTS1 entry-delay write-up) is outside this target.
- The close of label L pairs with the mid stamped L+1. Entry fill at t0 prices at the mid stamped t0 (the close of label t0-1 in the saved engine). Path index k reads the mid stamped t0+k.
- Mid spread: P[k] = (ln mid_a(t0+k) - beta ln mid_b(t0+k) - alpha - mu) / sigma, with the event's own saved beta, alpha, mu, sigma.
- Forward-fill of the PATH mid is allowed under section 3 (planner's ruling), never at entry, never at an exit price, and never from the close.

## 3. Entry, path, exit (planner's missing-mid ruling, fixed before any outcome is seen)
- ENTRY at t0 on REAL mids at stamp t0 for both legs, no fill. Either missing: the event is DROPPED, status no_entry_mid (counted).
- PATH mid (for the exit TRIGGER only): per leg, a missing mid at stamp t0+k is filled with the last real mid of that leg, for at most 5 consecutive missing minutes after it. A missing minute beyond the fifth stays missing. No fill from the close (it would bring bounce into the exit). The filled path is Pf[k]. The fill uses only mids stamped <= k, so it looks at nothing in the future; a stale filled leg can delay a trigger OR fire one the real path would not have fired (stated, not a defect). RECEIPT (build, printed): on a seeded sample of 20,000 events every mid stamped after k_trig is overwritten and the trigger scan re-run; trigger_k and exit_reason must be unchanged on all (the build stops otherwise).
- TRIGGER = the first k in 1..600 where both legs have a (real or filled) mid and s x Pf[k] <= 0 (reason mu). If none, trigger at k = 600 (reason timeout) when both legs have a (real or filled) mid at 600; if not, the event is DROPPED, status no_exit_mid (counted).
- EXIT PRICE = the first REAL (unfilled) mid at or after the trigger minute: the exit stamp is the first stamp k_x >= k_trig (k_x <= k_trig + 60) at which BOTH legs have a real mid. None within 60 minutes: DROPPED, status no_exit_mid_cap (a separate status from the other no_exit_mid causes). The checker accepted the 60-minute cap as a counted detail. Exit fee, exit half-spread and funding use the exit stamp k_x (k_x can be beyond 600; that is stored).
- CAP COUNT: before any label the build prints the number dropped by the 60-minute cap on its own line, by period, month and tier (separate from the other no_exit_mid causes). RULED (planner 2026-11-20): if more than 1% of test-month events are dropped by the cap, the build STOPS and reports to the planner before any label is built. The stop is in the code.
- ORDER OF THE BUILD (in the code): (1) the AVAILABILITY STAGE computes only mids, trigger_k, exit_k (k_x), status, gap runs, flags and sources; NO gross, return or y is computed or printed in it. (2) The two hard stops below are tested on the test-month events (denominator: ALL test-month events; the shares over the events that have entry mids are printed beside). (3) Only if both stops pass are the y components computed. The stops use the flag as defined here, over path minutes 1..k_x (cap-dropped events: 1..trigger+60; no_exit_mid: 1..600), NOT the 1..600 upper bound the sizing log used. A stop writes no label and exits with code 2. The build never prints y, gross or a return; step B reads y.
- Stored per event: trigger_k (-1 when no trigger exists), exit_k (= k_x; -1 unless status ok), exit_reason (1 mu, 2 timeout, 0 none), gap_flag, max_gap_len_leg, gap_flag_union, max_gap_len_union, n_filled (filled leg-minutes before the trigger).
- GAP LENGTH and FLAG (planner's ruling 2026-11-20: the fill is per leg, so the flag is per leg). For each leg, a gap is a run of consecutive path minutes with no real mid for that leg. max_gap_len_leg = the longest such run of EITHER leg inside path minutes 1..k_x (a run that touches k_x counts only up to k_x). gap_flag = (max_gap_len_leg > 5): an event is flagged if EITHER leg, on its own, has a missing run longer than 5. This per-leg flag is the HEADLINE: it drives the with / without split in step B and the 10% hard stop. SENSITIVITY only: gap_flag_union = a run of consecutive minutes where either leg is missing (the union) longer than 5, with max_gap_len_union; it over-flags (leg A missing 1-4 and leg B missing 5-8 give a union run of 8 although each leg is filled at every minute). The build prints both flags' shares, the union beside the per-leg one as a sensitivity line. Both are stored. Events are NOT dropped for a flag.
- Entry stretch in mid terms z0_mid = s x P[0] is stored. It can be <= 0 (the stretch was all close vs mid gap); such an event is kept (the signal came from closes) and triggers at the first minute k >= 1 with both mids, with its cost. The count is printed by period.
- PRINT BEFORE ANY LABEL IS BUILT (the build's availability stage, from the price tables only, no y): the gap-length distribution (buckets 1, 2, 3-5, 6-10, 11-30, 31+) and the share of events flagged, by period (search / vault / test months), by month and by liquidity tier. HARD STOP (on the per-leg gap_flag): if more than 10% of TEST-MONTH events are flagged, the build stops and the numbers go to the planner before any label is built. The stop is in the code, not a promise.
- Sizing so far (print-only, `diagnostics/s2_target_sizing.log`, the 11 local 2026 sample days, events with t0 before 14:00 UTC; full-window upper bound): events with a gap above 5 minutes: G8 alone, ctxs alone and either source are printed there. The G8-only period (2025-06 to 2025-12-19; the ctxs cache starts 2025-12-20; it holds 2,269,015 search events, about 1,996,406 from 2025-06 to 2025-11 and the rest in December) is NOT in that sample; its share is printed by the build before any label.

## 4. Gross (bp of N)
- Leg weights at entry: wa = 1/(1+|beta|), wb = |beta|/(1+|beta|), (wa + wb = 1; N = 1).
- Leg returns at the real mids: ra = exp(ln mid_a(exit) - ln mid_a(entry)) - 1, rb likewise (exit = exit stamp k_x).
- gross_bp = 1e4 x (wa x dir_a x ra + wb x dir_b x rb). Exit leg weights wxa = wa x (1 + ra), wxb = wb x (1 + rb) (the legs' value at exit as a share of N).

## 5. Costs (taker)
- Fee: 4.5 bp per fill on each leg's value: fee_in_bp = 4.5 x (wa + wb) = 4.5; fee_out_bp = 4.5 x (wxa + wxb) (the engine charges the exit fee on the exit leg value).
- Half-spread: G8 table spread_bp / 2 for the leg's coin at the entry stamp and at the exit stamp k_x, charged on the leg value: hs_in_bp = wa x hsa_in + wb x hsb_in; hs_out_bp = wxa x hsa_out + wxb x hsb_out. A leg-stamp whose G8 row is absent or crossed: use the nearest minute within +-1 (closer first, earlier on a tie); else the coin's median half-spread over the non-crossed rows of the same calendar month (labelled hs_imputed, counted by cause: day file absent / minute absent / crossed); a coin-month with no row: the event is DROPPED with status no_spread. The monthly median uses spreads stamped after t0 within the month: fine for a COST in a label, it must never become a feature.
- Funding: the hourly REALISED rate of the public fundingHistory API, per coin (fundinghist), as the engine (s1_profit1.py, funding block): for every hour boundary H with floor_hour(t0) < H <= exit stamp, flow_leg = -dir x rate_coin(H) x (leg value). The engine's check runs BEFORE its exit test on the same minute, so a boundary H equal to the exit stamp IS paid (the build does the same: H <= exit stamp). The engine pays NO flow for an hour that is missing in a coin's file (`h in fseries.index`); the build does the same and counts the events with at least one missing hour. The leg value is its ENTRY value (wa or wb), NOT marked to market (the engine marks it; the difference is second order; stated). funding_bp = 1e4 x sum over legs and hours of flow (positive = received). A coin without a funding file (9 coins in the event list, see sizing) gets funding 0 for that leg and the event is flagged funding_missing (counted).
- DEPTH IMPACT is NOT included. Check before step B reads any y, print-only on saved files (done in `diagnostics/s2_target_sizing.py`, log lines DEPTH CHECK): for the four COSTS1 taker runs, B - C per fill (the no-bounce section table) against the G8 half-spread per fill of the same runs (costs_legs.json: half_spread / (fees / 0.00045) x 1e4). The remainder (B - C minus half-spread) is a RESIDUAL, not a bound: B - C is on the matched trade set and the half-spread on the trades that have a G8 row (different trade sets), and B - C also includes the close-priced proxy rows and the +-1 minute rows. The planner reads that remainder against the step B result.
- y_taker = gross_bp - fee_in_bp - fee_out_bp - hs_in_bp - hs_out_bp + funding_bp.

## 6. Stored columns (one row per event; every component, so a maker variant can be derived without a rebuild)
event_id, side (search / vault), t0, status (ok / no_entry_mid / no_exit_mid / no_exit_mid_cap / no_spread; every event keeps its row, nothing is dropped or imputed beyond these rules), trigger_k, exit_k, exit_reason, src_in_a, src_in_b, src_out_a, src_out_b (0 none, 1 ctxs, 2 G8; src_out is the source of the exit mid at k_x), gross_bp, wa, wb, wxa, wxb, hsa_in, hsb_in, hsa_out, hsb_out (bp, half-spread per leg and stamp), hs_imputed (0 none, else the cause 1 day file absent / 2 minute absent / 3 crossed of the first median-imputed leg-stamp), hs_n_shift (leg-stamps priced from the +-1 minute neighbour), fee_in_bp, fee_out_bp, funding_bp, funding_missing, funding_hours_missing, y_taker, z0_mid, max_gap_len_leg, gap_flag (per leg, headline), max_gap_len_union, gap_flag_union (sensitivity), n_filled; status adds no_exit_mid_cap. `tier` (and `month`, `test`) are GROUPING labels for step B only: the tier is the COSTS1 test-period (search events) or vault-period (vault events) coin tier, not point-in-time, and must never be a feature in step C. (`entry_gap_flags` is dropped: the entry mids are real by rule, so there is nothing to flag.) A maker variant is derived from these as: fee 1.5 bp per fill instead of 4.5, no half-spread, funding and gross unchanged; the maker FILL (limit order fills, one-leg crossings, adverse selection) is NOT derivable from this table (it needs the 1-minute bars; COSTS1 section 3) and is not claimed.

## 7. Missing-data counts printed by the build (before any y is read)
By period (search / vault / test months), by month and by liquidity tier (COSTS1 tier mapping): events; status counts; source of the entry mids (ctxs / G8); the gap-length distribution and the gap_flag shares of both flags (section 3; the hard stop is on the PER-LEG flag, the union flag is a sensitivity line) and the cap count; the share of events whose entry source and exit source differ (src_in vs src_out, by period, month and tier); n_filled; share with hs_imputed by cause; share with funding_missing and with missing funding hours; share with z0_mid <= 0; the 21 G8 days absent from the archive are listed with the events whose window touches them. Receipts (printed): (RI) identity: the stored components (gross, fees, half-spreads, funding) reproduce the stored y_taker on every ok event, first in memory (float64, tolerance 1e-9 bp) and again on the written file read back (float32 columns, tolerance 1e-3 bp; values not printed); (R1) with CLOSE prices at the saved stamps the same formulas reproduce the saved gross_pnl of the eight COSTS1 headline runs' trades to 1e-4 (proves leg weights and directions); (R2) for the trades of the four TEST runs (the vault runs wait: vault discipline), the distribution of this build's mid exit minute against the saved close exit minute and of this build's funding_bp against the saved funding (printed, not asserted: the exit minutes differ by construction).

## 8. Output, vault discipline, where it runs (proposal; the planner and the user decide)
- Two output files: s2_labels_search.parquet and s2_labels_vault.parquet. RULING (planner relaying the user, 2026-11-20: "lets just update the dataset label"): the vault labels ARE built in this build, as part of the dataset. They are written to their own file, and NO step reads, prints or scores the vault file's y, gross or exit minutes until step C is finished and the planner calls the single vault scoring. The build prints for the vault only status counts, flags, sources and missing-data counts.
- The slim G8 table (coin, minute, mid, spread_bp, crossed) is built over ALL days, so it WILL hold vault-period price rows (prices only, no y). The vault y is computed in the same build (ruling above) and not read afterwards; the availability stage of section 3 prints counts only, no outcome.
- What "no vault outcome exists" means: for the NEW target only. COSTS1 and the S1 steps 3 and 5 already read vault results for the old picks (reach-mu and the profit engine). The vault is therefore not fresh in that sense; the user ruled the data fresh for the new target and the discipline above is the safeguard.
- Code and these rules go to the checker before any build. The build log, the counts of section 7 and a diff go to the checker before step B reads any y.
